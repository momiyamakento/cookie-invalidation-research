## 確定条件

- 登録60人、候補50人＋固定対照10人、10サービス、各利用者各サービス2セッション。
- バースト人数1/5/10/20/50。
- 主観測は当初設計の100 msを維持し、HTTP並列上限32とする。予備実験で最速だった条件を選ぶ方法は採らない。
- すべての人数について観測通信なしの参照条件を追加する。こちらでも直前・終了後に全Cookieを確認し、管理応答時間と最終状態を測る。保護到達時間は推定しない。
- 各人数・観測条件を3ブロック×10反復＝30回。計300測定バースト、5,160通知。ウォームアップは各ブロック各条件1回の計30バーストで別扱い。
- 同一ブロック・反復・人数では、両観測条件の対象者集合を同じにする。全10条件の実行順は反復内でseed付きランダム化。
- 観測期限は共通開始予定から30秒。個別確認要求のタイムアウトは2秒。通知は再送しない。管理からサービスへの1.5秒・最大3回・間隔300 msは既存のまま。
- 管理は毎試行新規起動・新規DB。サービスはブロックごとに再起動し、各試行で新規DBへ切り替える。初回失効通信の接続確立等を含む。
- 失敗や長い応答を除外しない。独立反復単位はバーストで、利用者ごとのp95は記述統計とする。
- 主実験中に別の負荷試験・回帰テストは実行しない。全プロセスが同一PCにある制約は維持される。

実行コマンド：

```powershell
npm run evaluate:concurrent -- --main --interval=100 --paired
```

## 解釈の制約

確認ありの保護到達時間には観測通信の影響と確認待ち時間が含まれる。確認なしの管理応答時間から実際のCookie拒否時刻を逆算しない。両者を単純に引いて補正しない。観測区間の幅を併記し、小さな時間差を過剰に解釈しない。

本測定は「新規起動した管理サーバーが処理するバースト」の評価であり、継続到着負荷・定常運転の最大性能ではない。前回の軽量メモリfixtureによる29 msなどの結果とも直接比較しない。
