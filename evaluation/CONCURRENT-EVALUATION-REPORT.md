# 複数利用者の同時検知評価：研究結果の要約

実施日：2026-10-08（日本時間）。実装、予備実験、本測定、独立再検証を完了。

## 何を明らかにしたか

囮Cookieの使用が検知されたことを前提に、同時に通知する利用者数を1〜50人に増やした場合の一括失効を評価した。
確認あり条件では2,580利用者試行の全対象Cookieで期限内の拒否を観測できた。人数が増えるにつれて所要時間が伸び、50人条件では再試行と長い管理応答も観測された。
対象外利用者のDB上の誤失効は0件だった。ただし、終了時の再確認には1試行で22件の通信・読取エラーがあり、最終HTTP確認まで全件成功したとは扱わない。

## 実装と実験条件

- 既存の管理サーバー・利用者対応付け・並列失効処理は変更していない。
- 多利用者SQLite評価サービス、バースト通知、独立プロセスによるCookie確認、時計校正、生データ保存、Pythonによる独立照合を追加。
- 登録60人・10サービス・各利用者各サービス2セッションを固定。同時通知人数のみ1・5・10・20・50と変えた。
- 確認通信あり（設定100 ms、同時上限32）と確認通信なしを各30回、3ブロックで比較。
- 本測定300バースト・5,160通知。ウォームアップ30バースト、予備実験48バースト、小規模確認2バーストを別に実施。
- 管理サーバーは試行ごとに新規起動。すべてローカルPC上で実行。囮が使われる確率は測定していない。

## 正確性と例外

|確認内容|結果（本測定）|
|---|---:|
|確認あり：全対象Cookieの期限内拒否を観測した利用者試行|2,580 / 2,580|
|管理DB・応答で成功と正しい対象対応を確認した通知|5,160 / 5,160|
|終了時DBで対象・対象外の状態がすべて一致したバースト|300 / 300|
|終了時にHTTP拒否を再確認できた対象セッション|103,183 / 103,200|
|対象外DBの誤失効|0件|
|終了時再確認の通信・読取エラー|対象17件、対象外5件|

例外は `b3-r8-n50-p100` の1試行。対象17セッションは12人分に相当する。
当該試行でも計測中に対象1,000Cookieすべての401を観測し、終了時DBは対象REVOKED・対象外ACTIVEだった。
しかし、終了時に応答取得・読取が完了しなかった22件は未確認として残した。保存された例外名はTypeErrorで、詳細なcauseは保存していないため根本原因は不明。
再実行による置き換えや除外は行っていない。

## 今回追加できた研究成果

1. **複数利用者の通知集中に対する正確性を検証した。** サービス別に異なる利用者IDを使い、対象者の全セッションを失効させることと対象外のDB状態を維持することを確認した。
2. **人数増加に伴う遅延と再試行を定量化した。** 50人条件の追加要求受付は、確認なし1,195件、確認あり4,828件。再送受付とDBの状態変更を分けて照合した。
3. **測定用通信自体の影響を示した。** 50人の管理応答平均は確認なし1.471秒、確認あり2.331秒。確認ありの数値を、確認通信がない場合の性能として扱えないことを明確にした。

一方、実行順・ブロックによる時間の変動もあった。例えば50人・確認ありの拒否観測平均は、各ブロックで約1.63 / 1.39 / 2.09秒だった。
CPU・DB・ネットワーク待ちのどれが変動の根本原因かを断定できる計測ではない。

## 主張の範囲

本結果は、新規起動した管理サーバーと固定構成のローカル評価サービスが処理するバーストの評価である。
「50人が性能上限」「実環境でもこの時間で保護できる」「継続的な通知をこの速度で処理できる」とは主張しない。
前回のメモリ上の単一セッションfixtureとは条件が違うため、数値を直接比較しない。

終了時確認のエラーを含め、全330試行のHTTP記録・DB・ランナー集計の独立照合を完了した。
関連テスト140件、TypeScript型チェック、追加TypeScriptファイルとテストのLintが通過している。
