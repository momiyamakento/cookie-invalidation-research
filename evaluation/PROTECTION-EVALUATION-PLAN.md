# 障害下の保護到達時間・応答整合性評価

作成日：2026-10-07（日本時間）。本測定前に条件・測定定義を固定する。予備実験は測定機構の動作確認のみとし、本測定の集計に混ぜない。

## 研究上の問い

1. 一部サービスが失効要求に応答しないとき、正常サービスで旧Cookieが拒否されるまでの時間はどう変わるか。
2. 管理サーバーの全体応答時間は、正常サービスの保護到達時間を表すか。
3. 失効処理後に応答だけが失われた場合、管理側の判定と実際のアクセス可否は一致するか。
4. 逐次方式では障害対象の処理順序が、正常サービスの保護到達に影響するか。

仮説：並列方式では正常サービスの失効が障害対象の再試行終了より先に進む。逐次方式では先頭の障害対象が後続を待たせる。失効後の応答欠落では管理側FAILEDと実際の旧Cookie拒否が同時に生じる。

## 評価システム

研究本体の管理サーバー、利用者対応付け、通知API、失効オーケストレーター、HTTPクライアントをそのまま使う。サービス側は既存service-kitの認証・要求検証ルーターに、評価専用のメモリ上セッションを接続する。サービスはlocalhostで1サービス1子プロセス、管理サーバーも別子プロセス。10サービスを使い、各サービス1利用者・1セッションとする。

各試行で新しいランダムCookieを発行し、全サービスが200を返すことを確認する。評価クライアントはそのCookieを保存して、失効中・失効後にも同じ値で保護エンドポイントへHTTPアクセスする。無効化済みなら401になる。失効要求は実際のBearer認証とHTTP経路を通る。Cookie値は生データに保存しない。これは評価用認証モデルであり、Campus SNSのブラウザデモや実運用サービスそのものではない。

管理クライアントの既定値：1試行のタイムアウト1,500 ms、最大3回、試行間待ち300 ms。障害時の概算待ち時間は 1,500×3＋300×2＝5,100 ms。既存設定・研究本体は変更しない。

障害モード：

- healthy：正常に失効して応答。
- before：認証済みの失効要求を受信するが、状態を変更せず応答もしない。
- after：セッションを失効し、同じrequestIdの再試行も冪等に扱うが、すべての応答を返さない。

障害を注入するのは失効APIだけであり、保護エンドポイントは稼働を継続する。ホスト全体の停止、TCP接続拒否、広域ネットワーク障害の再現ではない。afterは実パケット損失の再現ではなく、失効後に確認応答を観測できない状態のモデルである。

## 条件と反復

| 条件ID | 方式 | 応答停止の位置 | 障害対象 |
|---|---|---|---|
| healthy-parallel | 並列 | なし | なし |
| healthy-sequential | 逐次 | なし | なし |
| before-first-parallel | 並列 | 失効前 | 先頭1件 |
| before-first-sequential | 逐次 | 失効前 | 先頭1件 |
| before-last-sequential | 逐次 | 失効前 | 末尾1件 |
| before-three-parallel | 並列 | 失効前 | 1・5・10番目の3件 |
| after-first-parallel | 並列 | 失効後 | 先頭1件 |

各条件30測定＝3ブロック×10回。各ブロックで条件ごとにウォームアップ1回。計210測定＋21ウォームアップ＝231試行。ブロックごとに各方式の管理プロセスとDBを新規作成する。サービスプロセスは全ブロックで共用し、各試行でセッション・カウンターを初期化する。方式間で同じサービス群を使用する。

各反復で7条件の順番をFisher–Yates法で並べ替える。32bit LCGのseedは20261007。試行間に100 ms待つ。並列実験の同時起動を避ける。値による外れ値除去をしない。3ブロックは同一PC・同一実験セッション内の反復であり、独立した実運用環境サンプルではない。

## 時刻と指標

すべての時刻は評価クライアントのperformance.nowを使い、プロセス間の時計同期に依存しない。原点t0は管理サーバーへの検知POST送信直前。囮の使用・検知・通知生成に要する時間は含まない。

- T_complete：検知POSTの最終応答JSONを読み終えた時間。
- T_deny(i)：保存済みCookieに対する最初の401応答本文を読み終えた時間。
- T_healthy：障害を注入していない全サービスのT_deny(i)の最大。
- T_all：全サービスのT_deny(i)の最大。拒否を観測できないサービスがある場合はnull。0やタイムアウト値に置き換えない。
- 判定不一致件数：管理側FAILEDかつ最終Cookieアクセス401のサービス件数。
- 未失効件数：管理応答後の最終アクセスが200のサービス件数。

観測は各サービスにつき直列で、200応答後20 ms待って再アクセスする。401を受けたサービスの定期観測は終了する。管理処理終了後は全サービスに最終確認を行う。実際の観測周期はHTTP往復時間＋20 ms以上であり、固定20 ms精度とは呼ばない。

失効時刻の保守的な区間は「最後の成功要求の送信開始（なければt0）」から「最初の401の受信完了」までとする。T_denyは実際のサーバー内失効時刻の上側の観測値で、厳密な失効瞬間ではない。各区間幅と全プローブの送受信時刻・HTTP状態を保存する。管理処理終了時点で拒否されない対象について、無期限に未失効であるとは断定しない。

平均・中央値・nearest-rank p95・最小・最大、ブロック別の平均等を報告する。実行環境1台の記述統計であり、統計的有意差や実環境への一般化は主張しない。T_healthyの方式差、先頭／末尾差、正常／障害差を比較する。障害数比較は並列のみで、完全要因計画ではない。

## 整合性確認と保存

全試行で管理結果、実際のCookieのアクセス可否、サーバーの状態、要求回数、状態変更回数を照合する。正常対象はSUCCESS・401・1要求・1状態変更。beforeはFAILED・200・3要求・0状態変更。afterはFAILED・401・3要求・1状態変更・一意requestId 1件。

想定外のHTTP状態、到達不能、観測の失敗、整合性不一致は正常な研究結果として集計せず、実験を停止する。保存済み試行は保持し、完了summaryの有無で完遂を区別する。manifestには環境・条件・主要ソースのSHA-256を保存する。trials.jsonlは各試行の直後に追記し、旧実験を上書きしない。

## 実行

リポジトリルートで実行する。

```powershell
npm run evaluate:protection -- --dry-run
npm run evaluate:protection -- --smoke
npm run evaluate:protection
```

smokeは1ブロック・各条件1測定＋1ウォームアップ。結果は別ディレクトリになる。本測定は既定設定で十数分程度を見込む。

## 限界

失効APIは実装本体のプロトコルを使うが、サービスのDB負荷・多数セッション・通常アクセス負荷は再現しない。観測HTTP自体の負荷がある。ポーリングなしの性能とは比較しない。同時検知、障害復旧後の再失効、囮検知精度、実被害削減量は対象外。10サービスの結果を100サービスに外挿しない。
