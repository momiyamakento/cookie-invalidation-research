## 1. 目的と対象範囲

複数利用者の検知通知が集中したとき、現行の一括失効機構の失効完了率、利用者ごとの失効所要時間、対象利用者の識別の正確性を評価する。

研究の問い：

- RQ1：同時通知人数が増えると、利用者ごとの保護到達時間と管理応答時間はどう変わるか。
- RQ2：対象者の全既存セッションを失効させ、通知されていない利用者のセッションを維持できるか。
- RQ3：遅延・未完了が発生した場合、管理処理、サービス処理、送信・観測側のどこに影響が現れるか。

本評価は検知通知の送信から開始する。囮Cookieの使用確率・検知精度、実際の被害削減効果は対象外。障害復旧、JWT対応、同一利用者への重複通知、実際の囮使用からの測定は別実験とし、主実験に混ぜない。

初回は現行方式の特性を測る。キュー・並列数制限などの性能改善は結果を確認してから別バージョンで比較する。

## 2. 現行コードから確認した前提

| 対象 | 現在の動作 | 本評価での扱い |
|---|---|---|
| `apps/management-server/src/db/schema.ts` | principalとサービス別localUserIdを対応付ける。複数利用者を保存可能 | スキーマを原則そのまま使用 |
| `routes/benchmark-services.ts`、`routes/mappings.ts` | 評価サービスの登録と利用者対応の登録が可能 | 計測前にHTTPで登録・読戻し |
| `routes/detections.ts` | 通知ごとに認証・利用者解決・失効処理を実行し、初回は通常201を返す | 実際のAPIへ通知する |
| `services/invalidation-orchestrator.ts` | 1イベント内はPromise.allSettledで並列送信。確認したコードにイベント横断の同時送信上限はない | 現行parallelを固定。実際のネットワーク同時数と同義ではない |
| `site-revocation-client.ts` | 1回1,500 ms、最大3回、再試行間隔300 ms | 固定・manifestへ記録。高負荷でのタイムアウトも結果に含める |
| `evaluation/src/protection-fixture.ts` | 固定のprotection-user、1トークン、1つのactive状態 | 多人数評価には流用せず、新しいfixtureを追加 |
| `packages/service-kit/src/research-site/` | SQLite、トークンハッシュ照合、利用者単位の失効、要求の重複処理対策 | スキーマ・リポジトリ・失効ハンドラを再利用 |
| `routes/evaluation-metrics.ts` | 管理プロセスのCPU時間とメモリを取得可能 | 既存の評価用認証で取得。RSSをシステム全体のメモリと呼ばない |

現在のサービス内失効は、その時点の利用者のACTIVEセッションをすべて対象とする。本実験中は新規ログイン・対応関係の変更を行わない。

## 3. 構成

```text
評価コーディネーター（条件・初期化・検証・保存）
    ├─ 通知送信プロセス ── HTTP検知通知 ── 管理サーバー（既存実装、独立プロセス）
    │                                         ├─ HTTP失効要求 → 評価サービス01
    │                                         ├─ HTTP失効要求 → 評価サービス02
    │                                         └─ … → 評価サービス10
    └─ Cookie観測プロセス ── HTTP /protected ── 各評価サービス

各評価サービス：独立プロセス＋独立SQLite DB、複数利用者・複数セッション
送信・観測プロセス → 生ログ → 独立集計・照合プログラム
```

全プロセスを同じローカルPCで動かす。別プロセスでもCPU・メモリ・ネットワークスタックは共有するため、管理サーバー単体の最大能力とは主張しない。

送信と観測を分離し、観測処理のイベントループが通知発行を直接妨げることを抑える。プロセスの単調時計を直接引き算しない。計時は下記の同期手順に従う。

## 4. 利用者とセッション

- 各試行で登録者数を60人に固定する。対象候補50人と、常に対象外の対照10人を用意する。
- 各人は同じ10サービスに所属し、各サービスに有効なセッションを2個持つ。計1,200セッション。
- 同時通知人数Nだけを1・5・10・20・50と変える。登録人数・DBサイズの変化と通知負荷を分離する。
- 対象外は60−N人。固定の10人だけでなく、対象にならなかった全利用者を最終検証する。
- principalIdとlocalUserIdを同じ文字列にしない。サービスごとに利用者番号をseed付きで置換し、同一人物のlocalUserIdがサービス間で異なる構成にする。
- 通知元はservice01に固定する。失効先10件には通知元自身も含む。
- 対象者はseedで選び、条件・反復間でローテーションする。
- トークンは試行ごとに新規発行。生トークンはプロセス内だけで保持し、結果ファイルはsessionId・ハッシュで対応付ける。
- 失効対象ジョブ数はN×10、対象セッション数はN×10×2。正常完了時は各ジョブのrevokedCount=2を期待する。

2セッションにする目的は「1個だけ失効し、もう1個が残る」を検出すること。セッション数を増やす性能評価は今回は行わない。

## 5. 評価用サービス

SQLiteの既存research-siteスキーマ、ResearchSessionRepository、createResearchSiteSessionRevocationHandler、共通の認証付き失効ルーターを使用する。DBは試行ごとのファイルとし、計測外で作成・投入する。既存のスキーマとインデックスを維持する。

| API（新規fixture内） | 用途 |
|---|---|
| `GET /health` | 起動確認 |
| `GET /protected` | Cookieをハッシュ化し既存リポジトリで認証。有効なら200＋localUserId、失効済みなら401 |
| `POST /internal/v1/sessions/revoke` | 既存共通ルーター＋既存失効ハンドラで処理 |
| `POST /control/reset` | 計測外で試行ID・利用者・セッションを設定。処理中は拒否 |
| `GET /control/snapshot` | 利用者別状態・要求記録・実際に変更した行数を計測終了後に回収 |

control APIはloopbackでのみ公開し評価用認証を必須にする。デモ・研究用サービスA〜DのDBやポートを使用しない。

失効要求の受付数、requestId、処理開始・終了の同一プロセス内時間、変更件数を記録する。計測中は逐次コンソール出力を避け、上限付きバッファに記録して終了後に保存する。人工待ち時間は0、障害注入はなし。

## 6. 通知の同時発行と時刻

送信プロセスがN件のJSON・認証情報を事前生成し、共通の開始合図で発行する。各レスポンスを待って次を送る方式にはしない。通知のeventId・decoyIdは利用者ごとに一意とする。通知の自動再送は行わず、管理サーバーからサービスへの既存再試行だけを有効にする。

「同時」は完全な同時刻ではなくバースト投入と定義し、以下を必ず記録する。

- 共通開始合図から各通知のfetch呼出直前までの遅れ。
- 最後と最初の通知発行時刻の差（送信幅）。
- 各通知の応答時刻・HTTP状態・応答内容・通信エラー。
- 送信プロセスのイベントループ遅延と使用したHTTP接続設定。

performance.now()などの単調時計を使用する。通知送信とCookie観測の時計は、試行前後のIPC往復でオフセットと不確かさを見積もり、送信時計へ換算する。複数往復の最小RTTを使う方法・サンプル数（例えば20回）を実装時に固定し、RTT/2を少なくとも誤差として保持する。試行前後のずれも記録する。十分な精度が出なければ同一計時プロセス案へ戻し、計測設計を改訂してから本測定する。

サービス内部の単調時刻との引き算はしない。管理DBのDate.now()由来の所要時間は補助値で、HTTP観測の高精度時刻とは混同しない。

## 7. Cookie観測と測定負荷

対象者の2セッション×10サービスすべてを実際のHTTPで確認する。管理APIの成功応答だけで失効を判定しない。

- 予備設定：各Cookieの観測間隔100 ms、観測プロセス全体の同時HTTP数32、各Cookieにつき未完了リクエストは最大1件。
- 公平な巡回で観測し、順序はseedで入れ替える。遅れた周期を一気に取り戻す送信はしない。
- 初回401後は高頻度観測を止め、終了時に再確認する。
- 送信開始・応答完了・HTTP状態・返却localUserId・実観測間隔・スケジュール遅れを生ログに保存する。
- 401以外の5xx・タイムアウトを「失効」と判定しない。200で違う利用者を返した場合は正確性異常。
- 全対象外利用者は直前・終了後に確認する。処理中は固定10人の代表セッションを低頻度（1秒目安）で観測する。短い処理では処理中観測がない場合も明記する。DBの変更履歴も照合するが、対象外が瞬間的にも常に利用可能だったとは断定しない。

最大条件では1,000個の対象Cookieを観測するため、100 msごとの観測を保証しない。実際の観測間隔と誤差幅を報告する。

予備実験でN=1,10,50について、観測間隔50/100/200 ms、および計測中観測なし（終了後検証のみ）を比較する。管理応答時間・再試行・サービス処理時間への影響と観測誤差を確認する。無観測条件では保護到達時間を主張しない。観測負荷が大きければ負荷を下げ、粗い分解能を明記する。都合のよい時間を得るために観測条件を選ばず、選定理由と全予備結果を残す。

## 8. 指標の定義

利用者iの通知発行時刻をs_i、Cookie kの最後の成功確認のリクエスト開始をl_ik、最初の401の応答完了をd_ikとする。通知後の成功がなければ下限をs_iに置く。事前成功確認は通知前に必ず終える。

| 指標 | 定義・注意 |
|---|---|
| Cookie拒否観測時間 | d_ik−s_i。実際の失効時刻そのものではなく、拒否を観測した上限値 |
| 利用者の保護到達時間 | P_i=max_k(d_ik)−s_i。全20Cookieの401が必要 |
| 保護到達の区間 | [max_k(l_ik), max_k(d_ik)]−s_i。時計同期の不確かさを外側に加える。失効状態が単調であることが前提 |
| 管理応答時間 | 通知のレスポンス完了−s_i。HTTPエラーも別区分で時間を保存 |
| 利用者保護完了率 | 観測期限内に全対象Cookieの拒否を確認できた人数/N |
| セッション失効確認率 | 401確認済み対象セッション数/(N×10×2) |
| 対象外誤失効 | 対象外のREVOKED記録数、対象外401数、対象外の観測エラー数を別々に集計 |
| 管理完了率 | 管理結果で全対象SUCCESSとなった通知数/N。保護完了率と分ける |
| バースト排出時間 | 共通開始から全対象の拒否観測まで。未完了があれば未到達 |
| 有限バーストの完了速度 | 全員完了時のみN/バースト排出時間。継続負荷の最大スループットとは呼ばない |
| 補助資源指標 | 管理CPU時間の前後差、RSS/heapの前後値。ピークメモリはこの方法では得られない |

観測期限は最後の通知発行から30秒を暫定値とし、予備実験後に固定する。期限到達でも「30秒で失効」とせずnullと観測期限を保存する。管理応答がエラーでも期限まで観測を継続する。個別HTTPには有限のタイムアウトを設定して記録する。

## 9. 本測定計画

| 項目 | 初期設計 |
|---|---|
| 主条件 | N=1,5,10,20,50（5条件） |
| 固定 | 登録60人、10サービス、2セッション/人/サービス、parallel、障害なし、人工待ちなし |
| ブロック | 3ブロック。管理・サービスプロセスをブロックごとに再起動 |
| ウォームアップ | 各ブロック各条件1回、集計から除外 |
| 本試行 | 各ブロック各条件10回＝各条件30回、計150バースト |
| 通知件数 | 本試行合計2,580件。ウォームアップ別 |
| 条件順 | 各反復内で5条件をseed付きランダム化 |
| 基準条件 | N=1。初回は逐次方式との比較を追加しない |

各試行前に管理プロセスを停止して試行用の新規DBを準備し、起動・登録・読戻し・接続ウォームアップを行う。サービスのfixture状態も計測外で新規DBへ切り替える。初期化後に固定の安定待ち時間を置く。これによりイベント履歴の蓄積を人数の影響と混同しない。ブロック再起動はサービス側プロセスの持越し状態も切り替えるために行う。

全通知・全観測処理のsettleを待ってから後検証する。期限超過で残処理がある場合はプロセスを停止してDBを保存し、試行を打切りとして記録する。処理中のDB削除・resetは禁止。

試行が独立した反復単位。利用者ごとの分布を示しつつ、同じバーストの利用者を独立実験として扱わない。条件ごとに各試行の中央値・最大値・完了率を集計し、ブロック別結果も示す。利用者をまとめたp95は補助的な経験分位点とし、nearest-rank法を明記する。成功例だけの時間分布には必ず完了件数を併記する。

## 10. 正確性検証と異常の分類

計測前：全1,200セッションで200と期待localUserIdを確認。全対応表を読戻し、各principalの10対象が正しいことを確認。

計測後：

1. 全対象セッションを再確認し401、DB上のREVOKEDを照合。
2. 全対象外セッションを再確認し200と期待localUserId、DB上のACTIVEを照合。
3. 通知のeventId→principalId→10個のサービス別localUserIdを期待値と照合。
4. 正常試行ではイベントN件、ジョブN×10件、サービスごとの失効済みセッション2N件、各初回要求の変更件数2を確認。
5. 再試行が起きた場合、同じrequestIdの再処理による二重変更がないか照合。受付回数と変更件数を区別。
6. 401後の最終200があれば失効状態の逆戻りとして報告。

負荷によるHTTPエラー・タイムアウト・未失効・誤失効は評価結果として保存し、成功するまで再実行して置き換えない。初期化失敗・ポート競合・ログ欠損は測定基盤異常として区別し、元ログを残したうえで再実行理由を記録する。送信幅の拡大も黙って除外せず、発生負荷とともに報告する。

## 11. 保存形式と成果物

新規結果ディレクトリ `evaluation/results/concurrent-<timestamp>-<id>/` に保存する。

- `manifest.json`：全条件、seed、観測・時計同期設定、HTTP設定、Node/OS/CPU/メモリ、関連ソースハッシュ、起動引数、実行日時。
- `trials.jsonl`：試行・条件・対象集合・開始終了・異常区分。
- `notifications.jsonl`：eventId、principalId、通知の送信・応答時刻、HTTP・管理結果。
- `probes.jsonl`：試行、principalId、serviceId、sessionId、観測開始終了・状態・遅れ。
- `service-records.jsonl`：要求受付・処理時間・変更件数・重複状況。
- `clock-sync.jsonl`：IPC往復・オフセット・不確かさ。
- `snapshots/`：試行終了時の管理DB、サービスDB、期待対応表。生Cookieを保存しない。
- `summary.json`、`users.csv`、`conditions.csv`、図、評価報告書。

独立集計プログラムが生ログとDBから集計を再計算し、ランナーの結果を照合する。図は「人数と時間（誤差幅付き）」「人数と完了率」「利用者時間分布」「観測間隔と送信幅」を中心とする。

## 13. 主張できること・できないこと

本評価からは、固定環境と構成におけるバースト通知人数と保護到達時間・完了率の関係、対象利用者の分離の正確性を述べられる。

50人で問題がなかった場合も「最大50人まで」と上限認定せず「評価した50人の条件まで確認」とする。有限バーストの実験から継続到着負荷の処理容量は推定しない。管理・サービス・観測が同一PCなので、遅延を管理サーバーだけに帰属させない。必要なら結果を受けて持続負荷または別ホスト評価を別途設計する。

本評価の完了条件は、速い結果を得ることではなく、全試行の結果・失敗・観測誤差を再検証でき、研究の問いに条件付きで答えられることである。
