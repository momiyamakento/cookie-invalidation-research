# Management Server安全性評価

## 研究上の問い

中間発表で指摘された「管理サーバーを悪用して利用者を全サービスからログアウトさせられるのではないか」に対し、次を確認する。

1. 資格情報を持たない外部攻撃者が、対応表または検知イベントを変更できるか。
2. 1サービスの資格情報を持つ攻撃者が、別サービスになりすませるか。
3. 正規のサービス通信を維持できるか。
4. 現在の対策で防げない条件は何か。

## 脅威モデル

- 外部攻撃者は管理APIへHTTP要求できるが、Bearer資格情報を持たない。
- 単一サービス侵害者は、そのサービスのBearer資格情報を持つが、他サービスや管理サーバーの資格情報は持たない。
- 資格情報窃取者は、正しいサービスのBearer資格情報と対象のローカル利用者IDを知っている。
- 管理サーバーのOS・プロセスを完全に掌握した攻撃者は、今回のAPI認証では防げないため実験対象外とし、残存リスクとして扱う。

守る対象は、利用者対応表の完全性・機密性と、不正な検知イベントを起点とする可用性低下（強制ログアウト）の防止である。Cookieや通常セッショントークンは管理サーバーに保存しないため、その窃取はこの評価の対象ではない。

## 自動評価

```powershell
npm run evaluate:management-security
```

実装本体のManagement Server、SQLiteリポジトリ、Bearer認証、mapping API、detection APIを実HTTPで使用する。次の9ケースを実行し、HTTP結果とDBの変更件数を照合する。

- 未認証・不正トークンによる対応表登録
- Site AからSite Bへの登録・逆引き
- 正規のSite A対応表登録
- 未認証の検知通知
- Site AからSite Bへの検知元なりすまし
- 正規のSite A検知通知
- 窃取された正しいSite A資格情報による偽通知

結果は`evaluation/results/management-security-*/`の`summary.csv`、`summary.json`、`report.md`へ保存する。Bearer値、Cookie、パスワードは結果へ保存しない。

## 判定

未認証要求は401、サービス間の権限越境は403であり、拒否された要求でDB件数が変化しないことを成功条件とする。正規要求は201となり、必要なレコードだけが増えることを確認する。

正しいSite A資格情報を窃取した攻撃者によるSite A名義の通知は、現在の方式では正規通知と区別できない。このケースが受理されることも想定結果であり、隠さず残存リスクとして報告する。

## 2026年11月16日の実測結果

| ID | シナリオ | HTTP | DB件数 | 結果 |
|---|---|---:|---:|---|
| M1 | 未認証の対応表登録 | 401 | 0→0 | 阻止 |
| M2 | 不正トークンで対応表登録 | 401 | 0→0 | 阻止 |
| M3 | Site AがSite Bとして登録 | 403 | 0→0 | 阻止 |
| M4 | 正規のSite A登録 | 201 | 0→1 | 許可 |
| M5 | Site AがSite Bを逆引き | 403 | 2→2 | 阻止 |
| D1 | 未認証の検知通知 | 401 | 0→0 | 阻止 |
| D2 | Site AがSite Bの検知を偽装 | 403 | 0→0 | 阻止 |
| D3 | 正規のSite A検知通知 | 201 | 0→1 | 許可 |
| R1 | 窃取したSite A資格情報で偽通知 | 201 | 1→2 | 許可（残存リスク） |

9ケースすべてが事前に定めた想定結果と一致した。拒否された6ケースでは対象テーブルの件数が変化せず、正規要求2ケースでは必要なレコードだけが追加された。窃取資格情報のケースでは偽の検知イベントが追加され、Bearer資格情報だけでは正規通知と区別できないことを確認した。

## 評価の限界

本評価で直接測定したのは、Management ServerのHTTP受付結果とSQLiteの対応表・検知イベント件数である。D1・D2・R1について実際の全サービスのログアウト完了までは測定していない。正規検知から複数サービス失効までの動作は既存のE2Eテストおよび保護到達時間評価で別に確認している。したがって今回の結果は「不正な失効起点を作成できるか」の評価であり、攻撃時の実被害人数や可用性低下量の評価ではない。

## 次の候補

資格情報窃取時の影響を抑える対策として、短命な資格情報とローテーション、サービス・利用者単位のレート制限、監査ログと異常検知を候補とする。これらは誤検知時の正規失効遅延や可用性とのトレードオフがあるため、実装前に評価指標を固定する。
